# 役割 → サブエージェントへの落とし込み方（設計方針）

前提知識は [Claude Code サブエージェント公式ドキュメント](https://code.claude.com/docs/en/sub-agents)。
ここでは「調査した10役割を、どういう考え方でサブエージェントに変換するか」を設計する。

---

## 0. 先に結論

1. **役割の数だけエージェントを作らない。** 10役割 → エージェントは 7個、Skill が 2個、人間専任が 1個。
2. **エージェント同士は会話できない。通信路はリポジトリ上のファイルだけ。**
   → 設計の主対象は「エージェント」ではなく「**成果物の受け渡し規約**」。
3. **最初から全部作らない。** 3個から始めて、詰まった箇所に足す。

---

## 1. サブエージェントの性質（設計制約）

落とし込みの前に、道具の制約を押さえる。

| 性質 | 設計への影響 |
|---|---|
| 独立した context window を持つ | 会話履歴を引き継がない。**毎回ゼロから**。前提はファイルに書いておく必要がある |
| 返るのは要約テキストのみ | 大量ログ・検索結果を隔離するのに向く。逆に「対話しながら詰める」用途には向かない |
| `description` を見て自動委譲される | description は**説明文ではなくルーティング条件**。ここの品質＝使われるかどうか |
| `tools` / `disallowedTools` で権限を絞れる | レビュー役を read-only にする等、**事故防止のガードレール**として使う |
| `model` を選べる | 判断が重い役割は opus、機械的な役割は sonnet/haiku でコスト最適化 |
| `memory` で学習を蓄積できる | QA の既知の弱点、アートの決定事項など、繰り返し参照する知識に有効 |
| デフォルトで背景実行される | 並列に走らせられる。ただし同時 20 個まで |

---

## 2. 落とし込みの判断基準（3分類）

役割を機械的にエージェント化するのではなく、次の質問で振り分ける。

> **Q1. その作業は、あなたと何往復も対話しないと決まらないか？**
> → YES なら**サブエージェントにしない**（メインの会話 or Skill にする）
>
> **Q2. その作業は、大量の出力（ログ、検索結果、ファイル走査）を生むか？**
> → YES なら**サブエージェント向き**（context を汚さない）
>
> **Q3. その作業は、権限を絞ったほうが安全か？（read-only にしたい、等）**
> → YES なら**サブエージェント向き**（tools で強制できる）
>
> **Q4. そもそも AI が実行できるか？**
> → NO なら**人間の作業として明示**する（エージェント化して「できたふり」をさせない）

### 分類結果

| 元の役割 | 分類 | 理由 |
|---|---|---|
| プロデューサー | **メイン会話**（あなた＋オーケストレータ） | スコープ判断は対話そのもの。エージェント化すると指揮系統が二重になる |
| ゲームデザイナー | **Skill ＋ read-only エージェント** | 設計は対話で決める（Skill）／決めた後の整合性チェックはエージェント |
| ナラティブ／テキスト | エージェント | 文言の一括生成・一貫性チェックは自己完結 |
| UI/UX | エージェント | 画面仕様の起こしとレビューは自己完結 |
| ゲームプレイ実装 | エージェント | 実装＋検証で出力が多い。worktree 隔離も効く |
| テクニカルアート／パイプライン | エージェント | 規約チェック・最適化は機械的で出力が多い |
| アートディレクション | エージェント（※ただし「描く」役ではない） | 後述の注意点を参照 |
| オーディオ | エージェント（※同上） | 同上 |
| QA | エージェント | テスト実行ログの隔離＝最も教科書的な用途 |
| リリース／Steam入稿 | エージェント ＋ **人間専任** | 調査・下書きはエージェント／実際の申請・課金は人間 |
| マーケ／コミュニティ | エージェント | Web 調査が中心で出力が多い |

### ⚠️ 「できないこと」を役割名で誤魔化さない

これは設計上いちばん重要な注意点。

- **`artist` エージェントは絵を描けない。** 作るのは *アートディレクション*
  ——スタイルガイド、必要アセット一覧、命名規則、外注/生成AI 用の発注仕様書。
- **`composer` エージェントは作曲できない。** 作るのは *サウンドリスト* と *実装仕様*
  ——「どの操作でどの音が鳴るか」「BGM の遷移条件」「音量バランスの方針」。
- **`playtester` エージェントは代替にならない。** 第三者に遊ばせる工程は AI では置換できない。

役割名を `artist` ではなく **`art-director`** に、`composer` ではなく **`audio-director`** にするのは、
この境界を名前のレベルで固定するため。

## 3. 最重要：エージェント間の通信規約

サブエージェントは互いに会話しない。毎回まっさらな context で起動する。
したがって **「リポジトリ上のどのファイルを読み、どのファイルを書くか」** が実質的なインターフェースになる。
ここを決めずにエージェントだけ作ると、各自が勝手な前提で動いて破綻する。

### 3-1. 成果物の受け渡し（ハンドオフ）

```
docs/GDD.md                    ← 全エージェントが読む「憲法」
  │
  ├─→ docs/specs/<機能>.md      game-design-reviewer が整合性を検証
  │      │
  │      ├─→ 実装コード          gameplay-engineer が spec を読んで実装
  │      ├─→ docs/ui/<画面>.md   ux-designer
  │      └─→ tests/             qa-engineer が spec から受け入れ条件を導く
  │
  ├─→ docs/art/style-guide.md   art-director（→ アセット発注仕様）
  ├─→ docs/audio/sound-list.md  audio-director
  ├─→ docs/text/ja.csv          narrative-writer（ローカライズの原本）
  │
  └─→ docs/release/steam-checklist.md   steam-release-manager
      docs/marketing/plan.md            marketing-researcher
```

**ルール**
1. **書き込み先はエージェントごとに固定**。同じファイルを2つのエージェントが書かない（衝突防止）。
2. **`docs/GDD.md` は全員が読むが、書き換えられるのはメイン会話（＝あなた）だけ**。
3. エージェントは仕事の最後に、**担当ファイルを更新してから**要約を返す。
   （返り値の要約は消えるが、ファイルは残る＝次のエージェントが読める）

### 3-2. 共有前提は `CLAUDE.md` に置く

エージェントは毎回ゼロから起動するので、全員が知っておくべきこと
（エンジン、ターゲット、コーディング規約、スコープの線引き）はリポジトリ直下の
`CLAUDE.md` に書く。サブエージェントはこれを読み込んで起動する。

さらに横断的なルール（命名規則など）が育ってきたら **Skill** に切り出し、
`skills:` フロントマターで必要なエージェントにプリロードする。

## 4. 提案するエージェント構成

`.claude/agents/*.md` に配置する（プロジェクト単位。Git にコミットして育てる）。

| エージェント名 | 担当役割 | tools | model | 主な書き込み先 |
|---|---|---|---|---|
| `game-design-reviewer` | 設計整合性・**スコープ番犬** | read-only | opus | （レビュー結果を返すのみ） |
| `gameplay-engineer` | ゲームプレイ実装 | full | opus | ソースコード |
| `qa-engineer` | テスト実行・バグ再現・リグレッション | Bash/Read/Grep/Glob | sonnet | `tests/`, `docs/qa/` |
| `ux-designer` | 画面遷移・UI仕様・アクセシビリティ | Read/Write/Edit/Glob | sonnet | `docs/ui/` |
| `art-director` | スタイルガイド・アセット仕様・発注書 | Read/Write/Edit/Glob | opus | `docs/art/` |
| `audio-director` | サウンドリスト・音実装仕様 | Read/Write/Edit/Glob | sonnet | `docs/audio/` |
| `narrative-writer` | ゲーム内テキスト・一貫性・ローカライズ原本 | Read/Write/Edit/Glob | opus | `docs/text/` |
| `steam-release-manager` | Steamworks 要件・入稿チェックリスト・ビルド | Read/Write/Edit/Bash/WebSearch/WebFetch | sonnet | `docs/release/` |
| `marketing-researcher` | 競合調査・ウィッシュリスト施策・訴求文 | Read/Write/WebSearch/WebFetch | sonnet | `docs/marketing/` |

**エージェントにしないもの**
- プロデューサー → メイン会話（あなたと Claude 本体）が担う
- ゲームデザイン（決める側） → `/design` Skill として対話形式で回す
- テクニカルアート → 当面 `gameplay-engineer` に兼務させ、アセットが増えたら分離
- プレイテスト → **人間**

## 5. エージェント定義の書き方（テンプレートと実例）

### 5-1. フロントマターの使い分け

```yaml
---
name: agent-name          # 必須。小文字とハイフン。`:` は使えない
description: ...          # 必須。★ここが自動委譲のルーティング条件になる
tools: Read, Grep, Glob   # 省略すると全ツール継承。絞ることがガードレールになる
model: opus               # sonnet / opus / haiku / inherit（既定は inherit）
memory: project           # 学習を .claude/agent-memory/ に蓄積（任意）
color: blue               # 一覧での識別用（任意）
---
（ここから下がシステムプロンプト）
```

`description` の書き方が成否を分ける。**「何者か」ではなく「いつ呼ぶか」**を書く。

| ❌ 悪い例 | ✅ 良い例 |
|---|---|
| `QAの専門家です` | `テストの実行、バグの再現、修正後のリグレッション確認に使う。コード変更後は自動的に使うこと` |

「自動的に使うこと（use proactively）」を入れると、こちらから指名しなくても委譲されやすくなる。

### 5-2. 実例① スコープ番犬（read-only・最重要エージェント）

個人開発の最大の死因は**スコープの膨張**。それを止める役を、
**書き込み権限を持たない**エージェントとして独立させる。

```markdown
---
name: game-design-reviewer
description: 新しい機能・仕様の追加を検討したとき、GDD を更新したとき、実装前の仕様レビューが必要なときに使う。スコープの妥当性と設計の整合性を検証する。機能追加の話題が出たら自動的に使うこと。
tools: Read, Grep, Glob
model: opus
memory: project
color: red
---

あなたは初リリースを目指す個人開発プロジェクトの設計レビュアー兼スコープ管理者です。
実装は行いません。ファイルの変更もしません。検証と指摘だけを返します。

## 最優先の責務
このプロジェクトの最大のリスクは「機能の作りすぎで完成しないこと」です。
提案された機能に対して、まず次を判定してください。

1. その機能は `docs/GDD.md` に書かれたコアループに**直接**寄与するか？
2. 寄与しない場合、初回リリースから外して「将来検討」に落とせないか？
3. 実装コストの概算（時間規模：数時間 / 数日 / 数週間）はどれくらいか？
4. 数週間規模なら、同じ体験をより安く得る代替案はないか？

## レビュー手順
1. `docs/GDD.md` を読み、コアループとスコープ境界を確認する
2. `docs/specs/` の既存仕様を読み、矛盾・重複を探す
3. 対象を検証し、以下の形式で返す

## 出力形式
- **判定**: 採用 / 縮小して採用 / 却下（将来検討） のいずれか
- **理由**: GDD のどの記述に基づくかを引用して示す
- **既存仕様との矛盾**: ファイル名と該当箇所を明示（なければ「なし」）
- **縮小案**: 却下・縮小の場合、8割の価値を2割のコストで得る代替案を必ず1つ出す

判断に迷ったら「却下（将来検討）」に倒してください。
初リリースでは、削ることの失敗より、作りすぎることの失敗のほうが致命的です。
```

**設計意図**
- `tools` を read-only にして、レビュアーが勝手に実装を始めないよう**構造的に**防いでいる
- `model: opus` — 判断の質が直接プロジェクトの成否に効く箇所なので投資する
- `memory: project` — 過去に何を却下したかを覚えさせ、同じ議論の再燃を防ぐ
- 出力形式を固定 → 毎回同じ粒度で返り、比較・蓄積ができる

### 5-3. 実例② QA（大量ログの隔離）

```markdown
---
name: qa-engineer
description: テストの実行、失敗の調査、バグの再現手順の作成、修正後のリグレッション確認に使う。ゲームプレイのコードを変更した後は自動的に使うこと。
tools: Bash, Read, Grep, Glob, Write, Edit
model: sonnet
memory: project
color: green
---

あなたはこのプロジェクトの QA エンジニアです。

## 責務
1. テストスイートを実行し、**失敗したものだけ**を報告する
2. 不具合には、他人が再現できる手順を書く（前提状態 → 操作 → 期待 → 実際）
3. 修正後、その不具合と周辺機能の再検証を行う
4. 恒久的な知見は `docs/qa/known-issues.md` に追記する

## 報告の原則
- 成功したテストのログは**返さない**。合格数と失敗内容の要約のみ返す
- 失敗は「どのテストが」「どの入力で」「何を期待し」「何が起きたか」の4点で書く
- 原因の推測と事実を明確に分ける。推測には「推測:」と接頭辞を付ける
- 直せる範囲の明白な不具合は直してよいが、仕様判断が絡むものは直さず報告する

## 受け入れ条件の導出
`docs/specs/` に対応する仕様がある場合、そこに書かれた振る舞いを
テストケースに落とし込み、仕様との差分を指摘してください。
```

**設計意図**
- テスト実行ログは膨大 → まさにサブエージェントで隔離すべき典型例。返るのは要約だけ
- `model: sonnet` — 機械的な作業が中心なのでコストを抑える
- 「仕様判断が絡むものは直さず報告する」→ **越権の禁止**を明文化

## 6. 導入の順序（一気に作らない）

エージェントは作った瞬間から context と認知コストを食う。動く順に増やす。

### フェーズ1：企画を固める（今ここ）
まず `docs/GDD.md` と `CLAUDE.md` を**あなたとメイン会話で**書く。その上で1個だけ作る。

- ✅ `game-design-reviewer`

> この段階でエージェントを増やしても、参照すべき GDD がないので全員が推測で動く。

### フェーズ2：プロトタイプを作る
- ✅ `gameplay-engineer`
- ✅ `qa-engineer`

> 「コアループが面白いか」だけを検証する。アート・音・ストアは**まだ触らない**。

### フェーズ3：ゲームとして成立させる
- ✅ `ux-designer` / `art-director` / `audio-director` / `narrative-writer`

### フェーズ4：出す
- ✅ `steam-release-manager` / `marketing-researcher`

> Steam のストアページ審査 3〜5営業日、Coming Soon 最低2週間は**開発と並行できる**。
> フェーズ3の途中で `steam-release-manager` を前倒し起動するのが実務的に正しい。

## 7. 運用パターン

### 7-1. 直列につなぐ（設計 → 実装 → 検証）
```
game-design-reviewer で新機能の仕様をレビューして、
問題なければ gameplay-engineer に実装させ、そのあと qa-engineer で検証して
```

### 7-2. 並列で走らせる（依存のない調査）
```
art-director / audio-director / marketing-researcher を並列で走らせて、
それぞれ担当ドキュメントを更新させて
```
各エージェントが別 context で同時に動く。**書き込み先が重複していない**ことが前提（§3-1）。

### 7-3. 実装を隔離する
`gameplay-engineer` に `isolation: worktree` を付けると、
一時的な git worktree 上で作業する。実験的な実装で作業ツリーを汚したくないときに有効。

## 8. アンチパターン

| アンチパターン | なぜ駄目か |
|---|---|
| 20役割を20エージェントにする | 委譲先が曖昧になり、`description` が競合してルーティングが壊れる |
| `producer` エージェントを作る | メイン会話と指揮系統が二重化する。あなたが唯一の意思決定者であるべき |
| `artist` / `composer` という名前を付ける | 実行できない作業を担当させ、「やったつもり」の成果物が積み上がる |
| 全部 `model: opus` | 機械的作業にコストを払う。判断が重い役割にだけ使う |
| `tools` を全部継承にする | レビュアーが実装を始める、QA が仕様を書き換える等の越権が起きる |
| 成果物ファイルを決めずに走らせる | エージェント間で情報が繋がらず、毎回ゼロから推測される |
| GDD なしでエージェントを増やす | 全員が別々の前提で動き、成果物が食い違う |

---

## 9. 次にやること

1. `CLAUDE.md` を書く（エンジン、ジャンル、スコープ境界、規約）
2. `docs/GDD.md` を書く（コアループ、勝敗条件、プレイ時間、ターゲット）
3. `.claude/agents/game-design-reviewer.md` を作る（本ドキュメント §5-2 をそのまま使える）
4. GDD をレビューさせ、スコープを削ってからフェーズ2へ
