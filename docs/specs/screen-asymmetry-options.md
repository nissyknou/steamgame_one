# 設計判断：画面の非対称をどう実現するか

親文書: [`docs/GDD.md`](../GDD.md) §4 / [`CLAUDE.md`](../../CLAUDE.md) §2
状態: **判断待ち** — ユーザーが選択する

---

## 0. 前提となる事実

**Remote Play Together は映像を1枚しか作らない。**

ホストのPCがゲーム画面を描画し、その**映像をそのまま**相手に配信して、
相手の入力を受け取って返す。つまり「P1用の映像」と「P2用の映像」は存在しない。

- 分割画面にしても、**両者は1枚の画像の両方の半分を見る**
- 「相手にだけ見える情報」は**実装の工夫で回避できない**。方式そのものの帰結
- 真の別画面が必要なら、各PCがそれぞれ描画する＝**オンライン通信**が必須

---

## 1. 画面イメージ

### 案A：RPT ＋ 分割画面（現行 v0.2）

**存在する映像は1枚だけ。両プレイヤーがこれを見る。**

```
╔═════════════════════════╦═════════════════════════╗
║ P1 の空間 ── 1階         ║ P2 の空間 ── 2階         ║
║                         ║                         ║
║   ▓▓▓▓▓▓▓ ← 閉じた扉    ║   ░░░░░░░ ← 開いた扉    ║
║                         ║                         ║
║        ☻P1              ║           ☻P2           ║
║                         ║                         ║
║   [╱] レバー            ║   [╲] レバー            ║
║    └─ P2側の扉に作用    ║    └─ P1側の扉に作用    ║
╚═════════════════════════╩═════════════════════════╝
      ↑ P1 は P2 側の扉の状態もレバーの位置も見えている
```

**想定される会話**
```
P1「そっちのレバー引いて」    ← 見えているので聞く必要がない
P2「引いた」
P1「開いた」
```
→ **3語で終わる。** これが GDD §8 の仮説 H2 のリスクそのもの。

---

### 案B：独自オンライン（真の別画面）

**映像が2枚存在する。各プレイヤーは自分のものしか見えない。**

```
   P1 のモニタ                    P2 のモニタ
╔═════════════════════════╗   ╔═════════════════════════╗
║ 1階                      ║   ║ 2階                      ║
║                         ║   ║                         ║
║   ▓▓▓▓▓▓▓ 閉じている    ║   ║   ░░░░░░░ 開いた         ║
║                         ║   ║                         ║
║        ☻P1              ║   ║           ☻P2           ║
║                         ║   ║                         ║
║   [╱] レバー            ║   ║   [╲] レバー            ║
║    └─ 何に効くか不明    ║   ║    └─ 何に効くか不明    ║
║                         ║   ║                         ║
║   壁に文字：            ║   ║   床が抜けている         ║
║   「三つ数えて」        ║   ║   （P1には見えない）     ║
╚═════════════════════════╝   ╚═════════════════════════╝
```

**想定される会話**
```
P1「レバーがある。引いていい？」
P2「待って、こっち床が抜けてる。そっち何が見える？」
P1「壁に『三つ数えて』って書いてある」
P2「じゃあ数えて。せーの で引いて」
```
→ **状況を説明する会話**が発生する。これが本作の目指すもの。

---

### 案C：RPT ＋ 視界制限（折衷案）

**映像は1枚。ただし両サイドとも、キャラの周囲しか描画しない。**

```
╔═════════════════════════╦═════════════════════════╗
║▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓║
║▓▓▓▓┌────────┐▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓┌────────┐▓▓▓▓▓▓║
║▓▓▓▓│  ☻P1   │▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓│  ☻P2   │▓▓▓▓▓▓║
║▓▓▓▓│  [╱]   │▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓│  ░░░   │▓▓▓▓▓▓║
║▓▓▓▓└────────┘▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓└────────┘▓▓▓▓▓▓║
║▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓║▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓║
╚═════════════════════════╩═════════════════════════╝
   ↑ 扉の全体像は「どちらのプレイヤーにも」見えない
   ↑ 相手の可視範囲は小さいが、覗けば分かる
```

**効果**: 情報の絶対量が減るので、移動して確認し、報告する必要が生まれる。
**限界**: 相手の可視範囲を覗けば分かる。**真の非対称ではない**。

## 2. 比較表

| 観点 | **A: RPT ＋ 分割画面** | **B: 独自オンライン** | **C: RPT ＋ 視界制限** |
|---|---|---|---|
| **真の別画面** | ❌ 不可能 | ✅ 完全に実現 | ⚠️ 部分的（覗ける） |
| **隠された情報に依存する謎** | ❌ 作れない | ✅ 作れる | ❌ 作れない |
| **会話の質** | 「押して/押した」に痩せるリスク大 | **状況説明の会話が発生** | 中程度 |
| 実装コスト（通信） | **ゼロ** | 大（後述 §3） | ゼロ |
| 実装コスト（描画） | 分割画面のみ | 分割不要（各PCが1画面） | 分割＋視界マスク |
| QA の手間 | 1台で完結 | **常に2台必要。全テストが2倍** | 1台で完結 |
| desync バグ | 発生しない | **発生する。最も debug が困難** | 発生しない |
| 遅延の影響 | 映像遅延（操作にラグ） | 状態遅延（映像は各自ローカル＝滑らか） | 映像遅延 |
| 必要な購入本数 | **1本**（ホストのみ） | **2本**（両者） | 1本 |
| ペアあたり収益 | 1本分 | **2本分** | 1本分 |
| 友人が試す障壁 | **低い**（買わなくてよい） | 高い（買わないと遊べない） | 低い |
| プレイヤー母数 | RPT を知っている層 | オンライン協力を探す層（大きい） | RPT を知っている層 |
| 回線要件 | ホスト・ゲスト共に 10Mbps 以上 | 低速でも可（状態同期のみ） | 10Mbps 以上 |
| 初リリースの完走可能性 | **高い** | **中〜低**（初作としては要注意） | 高い |
| `CLAUDE.md` §3 との整合 | ✅ 適合 | ❌ **v1 対象外リストに抵触** | ✅ 適合 |

## 3. 案B のコストを正確に見積もる

「オンライン協力＝地獄」は**このゲームに関しては誇張**である。正確に評価する。

### 3-1. 本作が有利な理由

本作は**リアルタイムアクションではない**。同期すべきものが極めて少ない。

| 一般的なアクションゲームで必要 | 本作で必要か |
|---|---|
| 移動の予測・補間（prediction / interpolation） | ほぼ不要（低速移動） |
| ロールバック、遅延補正 | **不要** |
| 物理演算の同期 | **不要**（物理を使わない設計） |
| 高頻度の状態送信 | **不要**（スイッチ・扉の状態のみ） |
| チート対策 | **不要**（協力専用） |

同期対象は「プレイヤー2人の座標」「スイッチの状態」「扉の状態」「部屋の進行度」だけ。
**200ms の遅延を許容できる**設計にできる。

### 3-2. 使える既製部品

- **Godot 4 の高レベル API**: `MultiplayerSynchronizer` / `MultiplayerSpawner` / RPC
- **GodotSteam**: Steamworks SDK をラップ。Steam Networking Sockets（リレーサーバ、NAT越え）と
  ロビー・マッチメイキング・フレンドリストを提供。`MultiplayerPeer` として統合されるため、
  既存の RPC / レプリケーションのコードがそのまま動く

つまり **NAT越えとマッチメイキングは自作しなくてよい**。ここが最大の朗報。

### 3-3. それでも発生するコスト

| 項目 | 内容 |
|---|---|
| セットアップ | GodotSteam 導入、Steam App ID 取得（**先に $100 の Steam Direct 支払いが必要**） |
| ロビー・招待・参加フロー | UI と状態遷移。「ゲームを始める」までの導線を全部作る |
| 切断・再接続・セッション復帰 | 相手が落ちたらどうする？ 途中から再開できる？ |
| セーブデータ | 誰のセーブが正か。進行の同期 |
| **QA** | **常に2台のPC（または2つのSteamアカウント）が必要。全テストの手間が2倍** |
| desync デバッグ | ゲーム開発で最も再現・特定が難しい種類のバグ |
| 既知の制約 | `SteamMultiplayerPeer` はサーバーリレー非対応。クライアント間の中継に回避策が要る |

### 3-4. 見積もり

| 前提 | 通信機能の実装 | 全体への影響 |
|---|---|---|
| 経験者 | 3〜5週間 | QA 工数が恒常的に 1.5〜2倍 |
| **初めてゲームを作る人（本件）** | **2〜3ヶ月** | QA 工数が恒常的に 2倍＋ desync で詰まるリスク |

`docs/03-scope-management.md` §4 の観点では、これは
**「完成に必要な期間」を数ヶ月押し上げる**変更になる。

## 4. 収益への影響（見落とされやすい論点）

**RPT は1本の購入で2人が遊べる。** ホストだけが所有していればよい。

協力**専用**の本作では、これは直接的な意味を持つ。

| | ペアあたり販売本数 | 友人が試す障壁 |
|---|---|---|
| RPT | **1本** | 低い（買わずに参加できる） |
| オンライン | **2本** | 高い |

単純計算ではオンラインのほうがペアあたり収益が2倍。
ただし逆に、RPT は「友達がタダで試せる」ため**口コミの障壁が低い**。
`It Takes Two` が「フレンドパス」（2人目は無料）を意図的に採用したのはこの理由。

無名の個人開発初作では、**まず遊ばれること**の価値が高い可能性がある。
どちらが有利かは断定できない。**これは賭けの方向が違うだけで、優劣ではない。**

## 5. 案D：情報ではなく「労力」を非対称にする（RPT で使える技法）

真の隠蔽ができなくても、**分業を強制する**ことはできる。

- P2 側の壁に暗号（`◆●▲`）がある
- 解読表は **P1 側の部屋にしかない**
- 両者とも両方見えてはいるが、**同時に両方を読んで照合するのは認知的に困難**

情報は隠れていないが、**作業が分かれる**ので会話が発生する。
`Overcooked` や `Moving Out` が全情報可視でも players が叫び続けるのはこの原理。

**限界**: 本気で覗けば一人でも解ける。「解けてしまう」ことを許容できるかの問題。

---

## 6. 案E：段階的移行（推奨の落とし所）

**v1 は RPT で出す。ただしオンライン化しやすい構造で作っておく。**

[`docs/specs/coop-mechanic.md`](coop-mechanic.md) の現行設計は、実は**すでにネットワーク向き**である。

- 発信器は受信器を直接参照せず、必ず `signal_bus` を経由する
- A側と B側は**別の `World2D`** を持ち、物理・当たり判定が完全に分離している

この2点は、そのまま「状態を `link_id` 単位で同期する」構造になる。
後からオンライン対応する場合、**書き換えるのは transport 層だけ**で済む。

| 段階 | 内容 |
|---|---|
| v1.0 | RPT。分割画面。**完成させて出す** |
| v1.x | 売れたら、オンライン協力を無料アップデートで追加。真の別画面もここで実現 |

**リスク**: v1 のパズルは「隠された情報に依存しない」前提で作られるため、
オンライン化しても謎の質は自動的には上がらない。真の別画面を活かすには
パズルの作り直しが要る。**「後で足せる」のは通信であって、設計ではない。**

## 7. 判断のための問い

1. **「真の別画面」は、このゲームの成立に必須か、それとも強化か？**
   - 必須（それがないなら作る意味がない）→ **案B**
   - 強化（なくても成立するが、あったほうが良い）→ **案A/C/D/E**

2. **初リリースを完走することと、設計の理想、どちらを優先するか？**

3. **2〜3ヶ月の追加期間と、QA の恒常的な2倍化を受け入れられるか？**

---

## 8. 現状の推奨

**案A ＋ 案D ＋ 案E**（＝ v1 は RPT、労力の非対称で会話を作り、構造だけ将来に備える）。

理由は `docs/03-scope-management.md` §5 のとおり、
**「面白いかどうかの判明を遅らせない」**ことが最大のリスク管理であるため。

ただし §7-1 の答えが「必須」であるなら、**案B を選ぶべき**。
その場合は `CLAUDE.md` §3 の「オンラインネットコードを作らない」を
**明示的に撤回し**、プレイ時間 1〜2時間・部屋数 10〜12 のスコープを
さらに削って（例：3章構成、8室）期間を相殺すること。
