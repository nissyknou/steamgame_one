# スコープ管理 — なぜ「技術力」ではなく「スコープ」が個人開発を殺すのか

このプロジェクトの全判断の土台となる原則。
新機能を検討するとき、迷ったときは必ずここに戻ること。

---

## 1. コストの増え方の構造

ゲームの総開発コストはこう分解できる。

```
総コスト ≒ (機能数 N × 1機能あたりのコスト) + (機能どうしの組み合わせ N(N-1)/2 × 結合コスト)
                         ↑                                    ↑
                    技術力が効くのはココだけ            スコープが効くのはココ
```

決定的なのは、**技術力とスコープは効く場所が違う**こと。

- **技術力**は「1機能あたりのコスト」を下げる。線形の効果で、上限がある。
  熟練者でも初心者の 2〜3 倍速が現実的な上限で、10倍にはならない
- **スコープ**は「機能数 N」を決める。そして N は**二乗で効く項を持つ**

| 機能数 N | 機能間の組み合わせ N(N-1)/2 |
|---:|---:|
| 5 | 10 |
| 10 | 45 |
| 15 | **105** |
| 20 | 190 |

機能を 5個 → 15個（3倍）にすると、検証すべき組み合わせは 10 → 105 の **10倍**。
技術力が 3倍になっても追いつかない。**スコープは技術力で殴り返せない。**

この N² 項は実装ではなく、**バランス調整・バグ・QA** として現れる。
「実装できた＝終わり」と見積もると、この項が丸ごと抜け落ちる。

## 2. 1機能の「見えているコスト」は全体の1/5しかない

「二段ジャンプを足すだけ」で実際に発生する作業:

| 発生する作業 | 見えているか |
|---|---|
| ジャンプ処理の実装 | ✅ これだけが見えている |
| 2段目のアニメーション | ❌ |
| 専用の効果音 | ❌ |
| **既存ステージ全部の再設計**（届かなかった場所に届く＝難易度が全部壊れる） | ❌ |
| プレイヤーへの操作説明（チュートリアル、UI表示） | ❌ |
| 他機能との組み合わせ検証（壁ジャンプ中は？ 被弾中は？） | ❌ |
| セーブデータ互換、バランス再調整、リグレッションテスト | ❌ |

**「二段ジャンプを足す」は、実質「レベルデザインを全部やり直す」という意味。**

だから追加コストは「実装時間」ではなく **「既存の何を壊すか」** で見積もる。

## 3. 個人開発が構造的に脆弱な理由

チームには**プロデューサーという「ノーと言う専任者」**がいる。
個人開発では、企画する人・実装する人・進行を管理する人が**全部同じ人**。

そして人間の性質上、**企画は楽しく、実装は労働**。
だから内部で議論すると、いつも企画側が勝つ。ブレーキ役が構造的に存在しない。

> これが `game-design-reviewer` を **read-only（書き込み権限なし）** の
> 独立エージェントとして最優先に置いた理由。
> 自分の外側に「ノーと言う係」を、権限レベルで実装している。

---

## 4. 本当の締切は「納期」ではなく「モチベーションの残量」

```
完成に必要な期間  >  モチベーション・時間・資金が持つ期間   →  死
```

個人開発は生活の上に乗った無給の作業。勝負は納期ではなく、
**完成が先か、燃え尽きが先か**の競争になる。

- 技術力は左辺を**少し**縮める
- スコープは左辺を**桁で**変える（数ヶ月 ↔ 数年）

| 指標 | 数値 |
|---|---|
| インディー開発者が「スコープ過大」を失敗要因に挙げた割合 | **70%超** |
| スコープクリープが追加した期間（発生した60%のプロジェクトで平均） | **+4ヶ月** |
| ソロ開発者の失敗率 | 約 70% |
| 燃え尽きを経験した開発者 | 約 60% |

## 5. 「面白いか」の判明が遅れるのが致命的

- **小スコープ**: 2ヶ月で「面白くない」と判明 → 作り直せる
- **大スコープ**: 2年かけて「面白くない」と判明 → **引き返せない**

面白さは設計段階では確定できず、遊んでみないと分からない。
だから**「早く遊べる状態にする」こと自体が最大のリスク管理**。
技術力はこの判明時期を早めない。スコープだけが効く。

> 本プロジェクトのフェーズ1が「部屋3室だけの縦切りプロトタイプ」なのは、
> この原則の直接の適用。

## 6. 市場データ：「1本に賭ける」が最悪の戦略

2025年の Steam:

| 指標 | 数値 |
|---|---|
| 年間リリース本数 | 約 20,000本 |
| 新作の中央値売上 | **249ドル** |
| 売上 1,000ドル未満の割合 | 66% |
| レビュー1,000件に到達した割合 | **2.99%** |

**ヒットするかは事前に予測できない。**
予測できない以上、コントロールできるのは「**試行回数**」と「**1回あたりの学習量**」だけ。

- 3年かけた大作1本 = **試行1回**
- 6ヶ月 × 3本 = **試行3回**、しかも2本目以降は技術力が上がった状態

さらに、**技術力は「コードを書いた時間」ではなく「完成させた本数」で上がる**。
未完成のまま捨てたプロジェクトは、仕上げ・ストアページ・審査・リリース・ユーザー対応という
**最も学びの多い工程を一度も経験させてくれない**。

> 3年かけて放棄したプロジェクトより、3ヶ月で出し切った1本のほうが確実に上手くなる。

`Buckshot Roulette` はメカニクス実質1つ・Godot 製で 800万本売れた。

## 7. 判定ルール（毎回の判断に使う）

1. **コアループを1文で書けるか。** 書けないなら、まだ作り始めてはいけない
2. 新機能には常に「**これはコアループに直接寄与するか？**」を問う。しないなら v2 へ
3. 追加コストは「実装時間」ではなく「**既存の何を壊すか**」で見積もる
4. **迷ったら削る。** 削って失敗しても出せるが、作りすぎた失敗は出せずに終わる
5. 初リリースの目標は「良いゲーム」ではなく「**出し切ること**」。
   良いゲームは2本目以降で狙う
